# Vulnerability DB + CLI

Cтандартная библиотека Python 3.8+ и SQLite.

## Запуск

Пдразумевается что .json файлы находятся в папке проекта.

```bash
python load_data.py --rebuild            # создаёт vulns.db из vulnerabilities.json и versions.json
python vulncheck.py safe "Apache Tomcat"            # версии без уязвимостей
python vulncheck.py safe "Apache Tomcat" --latest   # только самая новая безопасная
python vulncheck.py info "Git for Windows" 2.40.1   # уязвимости версии
python -m unittest -v                    # тесты
```

Название продукта: сначала точное совпадение (без регистра), затем подстрока. Если подходит
несколько продуктов, инструмент выводит список; сузить можно через `--vendor`.
Коды возврата: 0 - всё чисто / успех, 1 - найдены уязвимости (или нет безопасных версий), 2 - ошибка ввода.

## Схема БД

```
vendors(id, name)
products(id, vendor_id -> vendors, name)
versions(id, product_id -> products, version, version_key)
advisories(id, kla_id UNIQUE, description, publish_date)
vulnerable_ranges(id, advisory_id -> advisories, product_id -> products,
                  start_version, fixed_version)
```

Почему так:
- производитель и продукт нормализованы, поскольку встречаются в обоих фидах;
- одна статья (`KLA_id`) относится к нескольким продуктам (Adobe Reader 2020 и DC, 7-Zip и 7-Zip MSI,
  Chrome и Chrome Enterprise) и к нескольким веткам версий (PostgreSQL, Git, Tomcat), поэтому
  описание и дата хранятся один раз в `advisories`, а пары «первая уязвимая - первая исправленная»
  в `vulnerable_ranges`;
- `version_key` - версия с компонентами, дополненными нулями, для сортировки на стороне SQL.

## Логика проверки версии

Сравнение версий числовое по компонентам (`8.5.9 < 8.5.11`). Одна статья может содержать
исправления сразу для нескольких веток (PostgreSQL `12.21.1`, `13.17.1`, `15.9.1`, ...), у всех
`start = 0`, поэтому наивное `start <= v < fixed` по каждой строке даёт ложные срабатывания
(PostgreSQL 12.5 «уязвим» из-за исправления 15.9.1). Правило:

1. внутри статьи выбирается ветка с самым длинным общим префиксом версии и исправленной версии;
2. версия уязвима, если `start <= v < fixed` для этой ветки;
3. если общего префикса нет ни с одной веткой, берётся самое раннее исправление статьи.

## Допущения

- «Вывести версию без уязвимостей» реализовано как список всех известных версий продукта
  (из второго фида) без известных уязвимостей; `--latest` оставляет только самую новую.
- Продукты, для которых в фиде нет записей об уязвимостях, считаются безопасными в известных версиях.
- Данные фида принимаются как есть: если статья указывает один диапазон `0 .. 133.0`
  (Thunderbird KLA77550), то уязвимыми считаются и ветки 115.x, и 128.x.
